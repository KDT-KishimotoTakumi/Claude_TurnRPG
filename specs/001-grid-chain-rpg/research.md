# Research: 盤面配置×技連鎖進化ターン制RPG

Phase 0 の成果。仕様に残っていた未決事項と、技術選定の判断をまとめる。「計画での決定」とした項目は、仕様では
決まっていなかったためこの計画が置いた仮の決定であり、異論があれば変更できる。

## 技術判断

### R-01 Unity のバージョンとパッケージ

- **Decision**: Unity 6000.0.42f1。Input System 1.11.2、uGUI 2.0.0、Test Framework 1.4.5（いずれも本機の Unity 6 同梱テンプレートで確認した版）。Code Coverage と Newtonsoft Json は導入時に解決した版を固定する。
- **Rationale**: 本機にインストール済みで、同梱テンプレートが検証済みの組み合わせである。
- **Alternatives**: 2022.3.22f1（旧 LTS）。新しい Input System の機能が不要なら使えるが、Unity 6 を選んだ。

### R-02 ロジックとビューの分離

- **Decision**: `TurnRpg.Core` を `noEngineReferences` の asmdef にし、MonoBehaviour を持たせない。View は Core の状態を読み、Core のコマンドを呼ぶだけにする。
- **Rationale**: EditMode で高速にテストでき、カバレッジの対象を境界で決められる（憲法 II・IV）。
- **Alternatives**: 全コードを 1 アセンブリに置き、属性でカバレッジ除外する案。除外の判断が曖昧になり、数値の水増しが起きやすい。

### R-03 決定論的な乱数

- **Decision**: Core に PCG32 を実装し、`IRandom` としてシードを注入する。`System.Random` と `UnityEngine.Random` は使わない。用途ごとに独立した乱数列を派生させる（ラン生成用、報酬用）。
- **Rationale**: 実装や実行環境が変わっても同じシードから同じ結果が得られる（FR-004、SC-004）。
- **Alternatives**: `System.Random(seed)`。Mono と .NET で実装が異なる可能性があり、結果の再現を保証しにくい。

### R-04 敵 AI（盤面評価）

- **Decision**: 1 手読みの貪欲探索。敵 1 体につき、移動先（最大 25 マス）×技×対象の候補を列挙し、各候補を適用した盤面を評価関数で採点して最大を選ぶ。評価関数は敵の種類ごとの重み（与ダメージ、撃破、被ダメージ、味方との隣接、目標の優先度）で定義する。同点は「移動先の座標順 → 技 ID 順 → 対象座標順」で決める。乱数は使わない。探索量の上限は候補数 1,000 件。
- **Rationale**: 仕様 FR-032 の「盤面を評価して最適な行動を選ぶ」を、決定論かつ短時間で満たせる。重みを変えるだけで敵の個性を作れ、偵察情報の「方針」にも対応する。
- **Alternatives**: 複数手先まで読むミニマックス。計算量が増え、50 ms の目標とテスト容易性を損なう。行動パターン表。仕様 FR-032 の「評価する」に合わない。

### R-05 UI の方式と入力

- **Decision**: 盤面は SpriteRenderer、メニューは uGUI。入力は Input System の Input Action アセットに集約し、`InputSystemUIInputModule` を使う。ゲームパッドとキーボードは方向キーとボタンでフォーカス移動、マウスはポインタ操作。盤面のマスは「カーソル位置」の概念を持たせ、3 デバイスで同じ操作列に正規化する。
- **Rationale**: uGUI はゲームパッドのフォーカス移動と相性がよく、E2E で `InputTestFixture` の仮想デバイスを使える。
- **Alternatives**: UI Toolkit。ゲームパッド操作の設定とテストの前例が少なく、この縦切りでは利点が薄い。

### R-06 中断セーブ

- **Decision**: Newtonsoft Json で Core の保存用 DTO を直列化する。`schemaVersion` を持つ。保存は「一時ファイルに書く → 検証して読み戻す → 本ファイルに置換」の順で、保存中の強制終了でも直前の保存が残る。読み込み失敗（形式不正、版数不一致、検証失敗）は例外を飛ばさずに結果型で返し、画面が通知する（FR-025）。
- **Rationale**: 破損に強く、ロジック（DTO 変換・検証・版数）を Core でテストできる。ファイル I/O だけを Game に置く。
- **Alternatives**: `JsonUtility` を Core で使う案。`UnityEngine` を参照するため不可。PlayerPrefs。内容の検証と置換の原子性を扱いにくい。

### R-07 データの外出し

- **Decision**: 技・敵・アイテム・装備の定義を `Assets/StreamingAssets/GameData/*.json` に置き、読み込み時に Core の `DataValidator` で検証する（参照切れ、派生先の循環、能力値の範囲、技が 24 種であること）。
- **Rationale**: 数値調整が容易で、データの整合性が EditMode でテストされる。
- **Alternatives**: ScriptableObject。Core が `UnityEngine` に依存してしまう。

### R-08 テストとカバレッジの実行

- **Decision**: `tools/run-tests.ps1` が Unity をバッチモードで起動し、EditMode と PlayMode を実行する。カバレッジは Code Coverage の CLI オプション（`-enableCodeCoverage`、`-coverageOptions "assemblyFilters:+TurnRpg.Core;generateAdditionalMetrics"`）で計測し、`tools/check-coverage.ps1` が結果の XML を読んで Core のラインカバレッジを検証する。90% 未満で非ゼロ終了する。
- **Rationale**: CI なしでも同じ手順で再現でき、品質ゲート（憲法）を機械的に判定できる。
- **Alternatives**: エディタ上で手動計測。再現性がなく、ゲートにできない。

### R-09 E2E と受け入れシナリオの対応

- **Decision**: 受け入れシナリオに ID（例: `US1-AS1`）を付け、E2E テストに `[Scenario("US1-AS1")]` 属性を付ける。EditMode の整合性テストが、仕様書の ID 一覧と属性を突き合わせ、E2E のないシナリオがあれば失敗する。
- **Rationale**: SC-008（1 対 1 以上の対応）を機械的に保証できる。
- **Alternatives**: 手書きの対応表のみ。更新漏れが起きる。表（`docs/e2e-traceability.md`）はテストから生成する。

### R-10 ドット絵

- **Decision**: ASCII の画素図（文字 1 つが 1 ピクセル）を `Editor` 側のスクリプトで PNG に変換し、4 職・敵 4 種・マス・UI 部品を作る。すべて自作で、出典は `docs/assets-licenses.md` に「自作」と記す。
- **Rationale**: ライセンスの懸念がなく、画素図がテキストなので差分管理しやすい。
- **Alternatives**: 外部素材。ライセンス確認と記録の手間が増える。

### R-11 リポジトリの置き場所とパス

- **Decision**: Unity プロジェクトを `game/` に置く。リポジトリは日本語パスの OneDrive 配下にあるため、最初のタスクでバッチモードの起動・テスト・カバレッジが動くことを確認する。動かない場合は ASCII のパスへのジャンクションを使う。`game/Library/` などは `.gitignore` に入れ、OneDrive の同期対象から外すことを推奨する。
- **Rationale**: 日本語パスと OneDrive の同期は、Unity の一部ツールで問題の原因になりうる。早期に検出するため。
- **Alternatives**: 最初から ASCII のパスにプロジェクトを置く。リポジトリ構成が分かれるため、問題が出たときだけ使う。

## 仕様で未決だった項目の決定（計画での決定）

### D-01 消耗アイテムの入手と補充

- **Decision**: ラン開始時に共有ストックとして「回復薬」2 個と「鼓舞の札」1 個を持つ。戦闘に勝利するたびに「回復薬」が 1 個補充される（所持数の上限は 4）。持ち込みは準備フェーズでストックから選び、戦闘で使わなかったものは持ち越す。
- **Rationale**: 体力が引き継がれる（FR-033）ため、回復の供給が難易度を決める。最小構成で毎戦闘に判断が生まれる量を置く。数値はデータで調整できる。

### D-02 アイテムと装備の種類

- **Decision**: 消耗品 2 種（回復薬: 対象の体力を回復、鼓舞の札: 対象の次の技の威力を上げる）、装備 4 種（攻撃・防御・素早さ・体力のいずれかを上げる）。装備は 1 人 1 つ。4 種すべてを最初から選べ、同じ装備を複数人に付けてもよい。
- **Rationale**: 効果の種類を少なくしてテストを網羅しやすくする。

### D-03 エッジケース

| 仕様の問い | 決定 |
|-----------|------|
| 倒れた味方の技は連鎖に挟めるか | 倒れたユニットは盤面から取り除かれ、行動も連鎖もできない |
| 盤面の端・占有マスでの移動・押し出し | 盤面外や占有マスへの移動・押し出しは起きず、その効果は無効になる（行動は消費する）。準備フェーズの配置は自陣内の空きマスへのみ。戦闘中の移動は盤面全体の空きマス |
| 同じ技の再進化 | 派生技は終端で、再進化しない |
| ボス戦での進化 | 進化は発生するが、ラン終了で破棄されるため保持の対象外 |
| 保存中の強制終了 | 一時ファイル経由の置換により、直前の保存が残る（R-06） |
| 入力デバイスの接続・切断 | 入力は最後に操作したデバイスに自動で切り替わり、切断されても他のデバイスで継続できる |
| 無効なシード | 0〜2,147,483,647 の整数のみ有効。範囲外・数字以外は拒否して理由を表示する。未指定は実行時に決める |

### D-04 設定画面

- **Decision**: 設定画面は作らない。音は扱わない（効果音と BGM はこの縦切りの対象外）。
- **Rationale**: 仕様の対象外項目に合わせ、最小の縦切りに集中する。音を扱う場合は別の仕様で追加する。

### D-05 ユニットの向き

- **Decision**: 向きは上下左右の 4 方向。技の使用時、プレイヤーは方向だけを選び、使用者はその方向を向く（対象マスは自動、data-model.md「対象マス」）。移動した場合は移動方向を向く。味方の初期の向きは敵側（上向き）で固定。導き手の「向きを変える」は、対象を指定した方向に向ける。
- **Rationale**: 範囲の計算を単純にし、テストの数を抑える。
