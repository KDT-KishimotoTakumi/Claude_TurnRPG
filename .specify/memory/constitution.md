# 盤面配置×技連鎖進化ターン制RPG Constitution

対象: Unity 6000.0.42f1 / C# によるターン制RPG（5x5 盤面、技の連鎖進化、準備フェーズ付きラン構造）。

## Core Principles

### I. テスト駆動開発（NON-NEGOTIABLE）
すべての振る舞いは Red → Green → Refactor の順で実装する。実装コードより先に失敗するテストを書き、
失敗を確認してから実装する。テストが先に存在したことをコミット履歴（テスト追加コミットが実装コミット
より前）で確認できなければならない。
**根拠**: 仕様と実装のずれを最小化し、リファクタリングを安全にするため。

### II. ロジック層のカバレッジ 90% 以上
Unity 非依存の純 C# ロジック層（ルール・戦闘・連鎖進化・ラン管理・セーブ）のラインカバレッジは
90% 以上でなければならない。90% 未満の変更はマージも完了報告も行えない。計測対象から除外してよいのは
View、MonoBehaviour、自動生成コードのみとし、除外対象の一覧を `docs/coverage-exclusions.md` に明示して
変更のたびに更新する。ロジックを除外一覧へ移して数値を満たす行為を禁止する。
**根拠**: 品質基準を計測可能にし、除外による数値の水増しを防ぐため。

### III. E2E テストの網羅（NON-NEGOTIABLE）
Unity Test Framework の PlayMode で、主要ユーザーシナリオを漏れなく自動化する。範囲は、起動 → 準備
フェーズ → 戦闘 → 勝敗 → ラン終了（ボス撃破／全滅）、ラン中断セーブからの復帰、ゲームパッド入力を含む。
仕様の受け入れシナリオ 1 件につき、最低 1 つの E2E テストを対応付け、対応表を維持する。対応する E2E の
ない受け入れシナリオが 1 件でもあれば、その機能は未完了とする。
**根拠**: ユニットテストでは検出できない画面遷移・入力・永続化の結合不具合を防ぐため。

### IV. ロジックと View の分離（Humble Object）
ゲームのルールと状態は View から分離した純 C# に置く。ロジックは asmdef で独立したアセンブリにし、
EditMode テストで検証する。MonoBehaviour は入出力の橋渡しに徹し、判断を持たせない。ロジック層は
`UnityEngine` を参照してはならない。
**根拠**: 高速な自動テストとカバレッジ計測を可能にするため。

### V. 決定論と再現性
乱数はシードを注入して生成し、同じシードと同じ入力列から同じ結果が得られなければならない。ロジック層で
`UnityEngine.Random`、`DateTime.Now` などの非決定的な API を直接呼ばない。ランの生成（敵編成・報酬）と
戦闘解決は、シード指定でテストできる。
**根拠**: バグの再現、バランス検証、安定した E2E テストのため。

### VI. 入力の抽象化と同等性
入力は Unity Input System を用いて抽象化し、キーボード・マウス・ゲームパッドで同じ操作が同等に行えなければ
ならない。ロジックは入力デバイスを知らず、抽象化した操作（決定・キャンセル・盤面カーソル移動など）だけを
受け取る。デバイス別の E2E テストを用意する。
**根拠**: ゲームパッド対応を要件として保証するため。

### VII. 仕様駆動（仕様なき実装の禁止）
実装は Spec Kit の順序（specify → clarify → plan → tasks → analyze → implement）に従う。仕様、計画、
タスクに存在しない機能を実装しない。仕様の変更は、先に仕様書へ反映してからコードに反映する。
**根拠**: 要件を細部まで確定させてから実装し、手戻りを防ぐため。

### VIII. 変更の規律と日本語
ドキュメントとコミットメッセージ、ユーザー向け文言は日本語で記述する。既存コードの命名・書き方に合わせ、
1 回の変更は小さく保ち、関係ない箇所に触れない。`.meta`、`Library/`、`Temp/`、`Logs/` は手編集しない。
シーンと Prefab の YAML も直接編集せず、必要ならコードまたはエディタ操作で行う。
**根拠**: レビューを容易にし、エンジン生成物の破損を防ぐため。

### IX. パフォーマンス規律
毎フレーム実行される処理（Update / LateUpdate / FixedUpdate）でメモリ確保（`new`、文字列連結、LINQ、
ボクシング）を行わない。`GetComponent` や `Find` 系は Awake / Start でキャッシュする。時間で変わる処理は
デルタタイムを用い、フレームレートに依存させない。
**根拠**: GC スパイクとフレームレート依存の不具合を防ぐため。

### X. 素材の出所とライセンス
ドット絵、音、フォントなどの素材は、自作またはライセンスが明記されたものだけを使う。第三者素材は出典・
作者・ライセンス・取得日を `docs/assets-licenses.md` に記録してから取り込む。出所が不明な素材は取り込まない。
**根拠**: 権利上のリスクを避け、配布可能な状態を保つため。

## 技術・品質制約

- 開発環境: Unity 6000.0.42f1（Unity 6）、言語は C#。
- テスト: Unity Test Framework（EditMode と PlayMode）、カバレッジ計測は Unity Code Coverage パッケージを
  用い、CLI のバッチモードで実行できること。
- アセンブリ構成: ロジック、View、EditMode テスト、PlayMode テストを asmdef で分離する。
- 入力: Input System パッケージ。プレイヤー向け UI は決定・キャンセル・移動の操作をすべて 3 種のデバイスで
  到達可能にする。
- 保存: ランの中断セーブのみ。メタ進行は持たない。保存データは版数を持ち、読み込み失敗時はゲームを
  クラッシュさせない。
- 視覚表現: 簡易ドット絵。素材は原則X に従う。

## 開発ワークフローと品質ゲート

マージまたは完了報告の前に、次をすべて満たさなければならない。

1. すべての EditMode テストと PlayMode（E2E）テストが CLI のバッチモードで成功する。
2. ロジック層のラインカバレッジが 90% 以上であり、除外一覧が最新である。
3. 受け入れシナリオと E2E テストの対応表に欠落がない。
4. `speckit-analyze` で仕様・計画・タスクの不整合に重大な指摘がない。
5. コード変更はレビュー（`code-reviewer`）を通過している。
6. 確認結果は実行したコマンドの出力を根拠として示す。実行できない確認は、できないと明記する。

## Governance

この憲法は他の開発慣行に優先する。改定は、変更内容と理由を記した文書化、プロジェクトオーナーの承認、
既存の仕様・計画・タスクへの影響の確認を経て行う。

- バージョニング: セマンティックバージョニングに従う。原則の削除や再定義は MAJOR、原則やセクションの追加
  と実質的な拡張は MINOR、表現の明確化は PATCH とする。
- 準拠の確認: すべての計画（plan）は憲法チェックを通し、違反がある場合は例外とその理由を複雑性の記録に残す。
  すべてのレビューで憲法への準拠を確認する。
- 例外: 原則 I、II、III は例外を認めない。
