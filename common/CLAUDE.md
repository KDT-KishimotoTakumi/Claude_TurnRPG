# 共通ルール

## コミュニケーション
- 回答は日本語で行う。
- 変更の前に方針を短く説明し、大きな変更は確認を取ってから行う。

## コーディング
- 既存コードの命名規則・書き方・コメントの量に合わせる。
- 1 回の変更は小さく保ち、関係ない箇所は触らない。
- マジックナンバーは定数にする。
- エンジンが生成するファイル（Unity の `.meta`、Unreal の `Intermediate/` `Binaries/` など）は手で編集しない。

## ゲーム開発での注意
- 毎フレーム呼ばれる処理（Update / Tick / メインループ）では、メモリ確保や重い検索を避ける。
- 時間で変わる処理にはデルタタイムを使い、フレームレートに依存させない。
- アセットのパスや名前を変えるときは、参照している箇所も確認する。

## 作業の進め方
- 調査 → 計画 → 実装 → コミットの順で進める。差分を一文で言える小さな修正は、計画を省いて直接行ってよい。
- 範囲を絞らない調査は `game-explorer` に任せ、メインの文脈を汚さない。
- 実装したら、ビルドやテストなど実行できる確認手段で結果を確かめ、成功したという主張ではなく出力を根拠として示す。確認できないものは、確認できないと伝える。
- エラーは症状を隠さず、根本原因を直す。
- 同じ指摘を 2 回直しても解決しないときは、方針を見直して仕切り直す。

## エージェントに渡す情報
- サブエージェントは CLAUDE.md を読まないことがある。守らせたいルール（触らないファイルなど）は依頼文に書く。

## コンパクト時に残すもの
- 変更したファイルの一覧、ビルド・テストのコマンド、未解決の問題。

## エージェントの自動選択
ユーザーに指示されなくても、作業内容に応じて次のエージェントへ自分で委譲する。

| 作業内容 | エージェント |
| - | - |
| 構成・処理の流れ・使用エンジンの調査、「どこで〜している？」という質問 | `game-explorer` |
| Unity（`Assets/` `ProjectSettings/`、C#、MonoBehaviour）の実装・修正・デバッグ | `unity-specialist` |
| Unreal Engine（`*.uproject`、`Source/`、UCLASS / Blueprint）の実装・修正・デバッグ | `unreal-specialist` |
| DXライブラリ（`DxLib.h`、`DxLib_Init`）の実装・修正・デバッグ | `dxlib-specialist` |
| コードを変更した後、完了を報告する前 | `code-reviewer` |

- エンジンが不明なときは、先に `game-explorer` で判別する。
- 1 つの依頼が調査と実装にまたがるときは、`game-explorer` → specialist → `code-reviewer` の順に呼ぶ。
- 1 行程度の修正や単純な質問は、委譲せずに直接行ってよい。
- 委譲するときは、目的・対象ファイル・守るルール（触らないファイルなど）を依頼文に含める。
